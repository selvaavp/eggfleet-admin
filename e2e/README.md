# EggFleet E2E Suite (Maestro + Playwright)

End-to-end coverage of the "A Day at EggFleet" scenario from
[`docs/e2e-test-plan.md`](../../docs/e2e-test-plan.md), driving **only the
real UIs** — the mobile driver app (Maestro, on an Android emulator/iOS
simulator) and the admin web app (Playwright, in a real browser). No test
setup or data creation goes through the API directly.

Two suites cooperate on one shared dataset:

- **Playwright** (`eggfleet-admin/e2e/`) — admin web: master data, inventory
  & assignments, payment/handover review, vendor payments & expenses,
  dashboard, notifications & edge cases.
- **Maestro** (`eggfleet/.maestro/`) — mobile driver app: login, deliveries,
  payment collection, cash/egg handovers, password/OTP flows, and the
  driver-side notification inbox.

Because some scenarios depend on actions in *both* apps (e.g. the admin
approves a payment, then the driver sees the "Payment Approved"
notification), the two suites must be run **in the order below**, sharing
the same data via `e2e/data/test-data.ts` and the same `E2E_RUN_ID`.

## Prerequisites

- `eggfleet-service` running at `http://localhost:3000` (`/api/v1`)
- `eggfleet-admin` dev server running at `http://localhost:5173`
  (`npm run dev` from `eggfleet-admin/`)
- An Android emulator (or iOS simulator) booted with the `eggfleet` app
  installed (`com.eggfleet.app`), and a seeded admin user matching
  `e2e/data/test-data.ts`'s `admin.email` / `admin.password`
  (`admin@eggfleet.local` / `Admin123!` by default)
- [Maestro CLI](https://maestro.mobile.dev/) installed
  (`~/.maestro/bin/maestro`)
- From `eggfleet-admin/`: `npm install` (installs Playwright + `tsx`)

## Running the full pipeline

```bash
cd eggfleet-admin
E2E_RUN_ID=100002 ./e2e/scripts/run-e2e.sh
```

`E2E_RUN_ID` seeds every name/phone/van-number/route-name created by the
run, so each run is isolated from prior ones in the same database.

### Starting from a clean database

`E2E_RUN_ID` avoids collisions with *prior* runs, but the dev DB otherwise
keeps accumulating data, which can affect "current state" assertions (e.g.
dashboard totals, notification ordering). To start from a clean slate, wipe
all data and re-seed just the admin user
([`eggfleet-service/scripts/reset-local-db.ts`](../../eggfleet-service/scripts/reset-local-db.ts),
run via `npm run db:reset:local`), then run the pipeline:

```bash
# Reset + full pipeline in one go
E2E_RUN_ID=100002 ./e2e/scripts/run-e2e.sh reset-and-run

# Just the reset (no E2E_RUN_ID needed) -- truncates every table and
# re-creates admin@eggfleet.local / Admin123!
./e2e/scripts/run-e2e.sh reset
```

The reset truncates every table (`TRUNCATE ... RESTART IDENTITY CASCADE`,
safe with `synchronize: true` — schema is untouched) and inserts one ADMIN
user matching `e2e/data/test-data.ts`'s `admin.email`/`admin.password`
(override with `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` / `SEED_ADMIN_NAME`
env vars). With an empty DB, `E2E_RUN_ID` can be reused safely since there's
nothing left to collide with.

Other modes:

```bash
# Admin web only (Phase 1/2 master-data setup + Phase 4-9 review/edge cases)
E2E_RUN_ID=100002 ./e2e/scripts/run-e2e.sh playwright

# Mobile only (assumes Phase 1/2 admin setup already ran for this E2E_RUN_ID)
E2E_RUN_ID=100002 ./e2e/scripts/run-e2e.sh maestro
```

## Pipeline order (and why)

| # | Step | Tool | What it covers |
|---|------|------|-----------------|
| 1 | `01-master-data.spec.ts` | Playwright | Phase 1 — vendors, routes, stores, vans, drivers |
| 2 | `02-inventory-assignments.spec.ts` | Playwright | Phase 2 — inventory batches, van assignments/loads, damaged eggs (also creates the "New Van Assignment" notifications for 8.1/8.2) |
| 3 | `01-d1-login.yaml` … `10-d1-forgot-password.yaml` | Maestro | Phase 3 — D1/D2 login, deliveries, payment submission, cash/egg handover submission, change/forgot-password flows (9.16-9.18) |
| 4 | `04-payments-admin.spec.ts` | Playwright | Phase 4 — admin review/approve/reject of submitted payments |
| 5 | `05-handovers-admin.spec.ts` | Playwright | Phase 5 — admin review/approve/reject of submitted handovers |
| 6 | `06-vendor-payments-expenses.spec.ts` | Playwright | Phase 6 — vendor payments & expenses |
| 7 | `07-dashboard-reconciliation.spec.ts` | Playwright | Phase 7 — dashboard totals reconcile with Phases 1-6 |
| 8 | `08-notifications-edge-cases.spec.ts` | Playwright | Phase 8 (admin side) + Phase 9 edge/negative cases |
| 9 | `11-d1-notifications.yaml`, `12-d2-notifications.yaml` | Maestro | Phase 8 (mobile side) — D1/D2 see the van-assignment, payment-decision and handover-decision notifications generated by steps 2/4/5 |
| 10 | `09-driver-deactivate.spec.ts` | Playwright | 9.5 setup — admin deactivates D2 |
| 11 | `13-d2-login-deactivated.yaml` | Maestro | 9.5 — D2's login is blocked with "Account is deactivated. Contact admin." |
| 12 | `10-driver-reactivate.spec.ts` | Playwright | 9.6 setup — admin reactivates D2 |
| 13 | `14-d2-login-reactivated.yaml` | Maestro | 9.6 — D2 can log in again |

Steps 10-13 are interleaved because the status toggle only exists in the
admin UI but the pass/fail check only exists on the mobile login screen.

## Customizing the data

Edit [`e2e/data/test-data.ts`](data/test-data.ts) — vendors, routes, stores,
vans, drivers, inventory batches, assignments/loads, deliveries, payments
(amounts/methods/approve-or-reject), handovers, vendor payments and
expenses. All downstream totals (delivery totals, store balances, vendor net
profit, dashboard reconciliation, handover cash pre-fill, etc.) are derived
from these values via the `F1`-`F15` formula helpers at the bottom of the
file, mirroring the formulas in `docs/e2e-test-plan.md` §2 — so changing a
quantity or rate automatically flows through every assertion.

Names/phone numbers/van numbers are derived from `E2E_RUN_ID` to avoid
unique-constraint collisions across runs. **Use a new `E2E_RUN_ID` for every
full pipeline run** — Phase 1/2 (`01-master-data`, `02-inventory-assignments`)
create records that are unique per `E2E_RUN_ID` and will fail with duplicate
errors if re-run against an `E2E_RUN_ID` that has already completed Phase 1/2.

Maestro flows read their data from the same file via
[`e2e/scripts/generate-maestro-env.ts`](scripts/generate-maestro-env.ts),
which `run-e2e.sh` invokes automatically and passes to `maestro test` as
`-e KEY=value` flags (driver phones/names, store names, batch rates,
delivery quantities, and the formatted payment/handover amounts shown in
notifications).

Other environment variables (all optional, see `e2e/data/test-data.ts`):

- `E2E_BASE_URL` — admin web URL (default `http://localhost:5173`)
- `E2E_API_BASE_URL` — backend API URL (default `http://127.0.0.1:3000/api/v1`)
- `E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD` — admin login used by
  `e2e/setup/auth.setup.ts`
- `E2E_DATE` — scenario date for assignments/deliveries/payments/handovers/
  expenses (default: today)

## Running an individual spec/flow

```bash
# Single Playwright spec (admin must already be authenticated via auth.setup.ts,
# which runs automatically as the `setup` project dependency)
E2E_RUN_ID=100002 npx playwright test e2e/tests/04-payments-admin.spec.ts

# Single Maestro flow
export PATH="$HOME/.maestro/bin:$PATH"
args=()
while IFS='=' read -r key val; do args+=(-e "$key=$val"); done \
  < <(E2E_RUN_ID=100002 npx tsx e2e/scripts/generate-maestro-env.ts)
(cd ../eggfleet/.maestro && maestro test "${args[@]}" 01-d1-login.yaml)
```

## Known gaps

Documented at the top of
[`08-notifications-edge-cases.spec.ts`](tests/08-notifications-edge-cases.spec.ts):

- **9.1, 9.9** — backend returns an unhandled 500 (instead of a clean 4xx)
  for certain duplicate-creation cases (DB-level UNIQUE constraints on
  vendor phone / van assignment), so the spec asserts the create still fails
  (and no record is created) rather than a specific status/message.
- **9.11** — `admin-inventory.service.ts createVanLoad()` has no
  duplicate-batch check; the spec asserts the Assign Van modal's
  client-side "combined load exceeds available stock" warning instead.
- **9.15** (create → delete → verify inventory restoration) — dropped: this
  single-pass seed's two assignments (A1, A2) already occupy every
  driver×van slot for today, so no new "today" assignment can be created to
  then delete.
